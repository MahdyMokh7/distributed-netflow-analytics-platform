| Rank  | Optimization                                                                      |                                  Likely storage impact | How good an idea?                         | Why                                                                                  |
| ----- | --------------------------------------------------------------------------------- | -----------------------------------------------------: | ----------------------------------------- | ------------------------------------------------------------------------------------ |
| **1** | Consolidate rows across `batch_id` / remove `batch_id` from logical cube identity |         **Potentially enormous — possibly tens of GB** | **Excellent if semantics allow it**       | Same logical aggregate/window currently appears multiple times for different batches |
| **2** | Redesign/remove redundant indexes                                                 |                                **~10–20+ GB possible** | **Excellent, after checking query plans** | Indexes are ~44 GB total; several overlap heavily                                    |
| **3** | Change IPs `varchar(45)` → `inet`                                                 | **Several GB, potentially ~5–10 GB including indexes** | **Excellent**                             | Smaller, semantically correct, validates IPs, also shrinks PK/index keys             |
| **4** | Connection SHA-256 `varchar(64)` → raw `bytea(32-byte)`                           |                                         **Several GB** | **Excellent**                             | You're storing a 32-byte hash as 64 ASCII bytes, including inside an ~11 GB PK       |
| **5** | Packet/count `BIGINT` → `INTEGER` where safe                                      |                                           **~2.5 GB+** | **Very good**                             | Current observed values are far below 2.1B; half the storage per counter             |
| **6** | Remove unused surrogate `id BIGINT` columns                                       |                                          **~1.5–2 GB** | **Very good if truly unused**             | They are not even part of the logical PK in most tables                              |
| **7** | Remove `window_end`                                                               |                                            **~2.1 GB** | **Good if window duration is fixed**      | It is derivable from `window_start + fixed duration`                                 |
| **8** | Remove `ingested_at`                                                              |                                            **~2.1 GB** | **Only if genuinely unused**              | Useful operational metadata, so storage saving alone may not justify removal         |
